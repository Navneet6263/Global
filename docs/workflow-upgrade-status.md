# Document-aligned workflow upgrade: implementation status

9 September 2026. Compared with the IDs in [the consolidated gap register](../../Sapling-Consolidated-Missing-Items-2026-09-08.md), using the current working-tree code. The register describes the earlier audit baseline; this document records changes since that baseline. It is not a claim that every requirement, browser journey, external provider or deployment check is complete.

**Implemented** means the stated bounded application capability is present in backend/UI source. **Partial** means useful capability exists but an important part of that requirement remains. **Not implemented** means the identified capability is still absent. **Deferred / decision** marks conflicting, later-phase or externally scoped requirements. Tests, builds and migrations must be reported separately with their actual execution results.

## Core workflow: W01-W12

| ID | Status | Current capability and boundary |
| --- | --- | --- |
| W01 | Implemented: bounded multi-service intake | One case accepts up to four distinct selected packages, retaining a primary package for compatibility. Each has a persisted service family, declarations/configuration, required-document snapshot, contracted price/tax/TAT and service-linked checks/results. Consent, manager approval and final release remain case-level gates; independent service-level release is not introduced. |
| W02 | Partial | HireCheck, IntegrityCheck, LeaderCheck and VendorCheck have service-family configuration, specialised check types and intake fields for organisation/registration/GST, conflicts, directorships, declarations and references. Vendor business name/registration are required. This is not a complete dedicated system for each specialisation: rich director/promoter subrecords, full resume-discrepancy handling and authoritative external company/watchlist/media searches remain beyond these fields. |
| W03 | Partial | Digital, Manual and Third-Party request/response records, source/provider/contact/reference/due date, exact reviewed evidence-version references, outcomes and reconciliation are implemented. All active method responses must finish; the consolidated result cannot conceal a recorded discrepancy or inconclusive result. They are selectable methods, not three mandatory sequential stages. Digital/third-party results are recorded by authorised humans; no provider API call or automatic provider callback is claimed. |
| W04 | Implemented | Package-required documents are snapshotted at intake. Start verification requires accepted consent and current reviewed, unexpired required documents; corrected/rejected evidence cannot be ignored. Legacy cases with no policy snapshot are not retroactively assigned a later package policy. |
| W05 | Implemented | Staff can verify, reject or request reupload against a specific current document version, with rationale, reviewer/time, optimistic version control and audit history. New uploads reset review. File validation/malware checks remain separate from human authenticity review. |
| W06 | Implemented: controlled correction path | An adverse/inconclusive result cannot be finalised without a resolved, linked clarification for the current review cycle and re-verification. Resolving linked clarification starts a fresh check cycle/task and method requests; old method results are retained as superseded history. QA cannot accept unresolved source work or evidence problems. A factual adverse outcome is not an automated hiring/character decision. |
| W07 | Implemented | QA readiness and final approval check reviewed required documents, current method evidence, unfinished field work/supervisor review and unresolved clarifications. These server-side rules supplement completed checks and the human QA checklist. |
| W08 | Implemented | QA approval enters `MANAGER_REVIEW`. An independent Operations Manager or Platform Admin records approval or returns work, with recommendation and audit evidence. The approver cannot be the same case's QA reviewer or factual verification/source-response author. No separate Manager login role was fabricated. |
| W09 | Partial | Highest recorded check risk updates case risk, and high-risk manager approval requires explicit acknowledgement. Manual escalation and timed operational reminders exist. A configurable multi-level high-risk escalation/recipient policy is not implemented. |
| W10 | Implemented | Authorised manager reopening selects checks, records a reason, increments review cycles and restarts methods. Earlier report records become superseded; files/snapshots remain preserved. Reopened reports require a new controlled review/release path. |
| W11 | Implemented under explicit payment policy | Manager approval -> immutable snapshot -> report preparation -> report-bound invoice -> full recorded cash payment -> release -> client download. Partial payments, credit notes and zero-value scopes do not bypass the gate. Legacy already-published workflow-v1 reports remain readable without automatic rebilling. This is not a payment-gateway integration. |
| W12 | Implemented | Controlled final closure follows completed/released readiness. Physical client download is not made an extra closure requirement. Closure does not execute a new whole-case retention/deletion lifecycle. |

## Decisions, external services and verification boundary

- **Consent withdrawal:** deliberately excluded from operational UI/API because the revised clarification conflicts with earlier Kaagaz text; no legal interpretation is claimed. Request tracking is not a hidden withdrawal/erase action.
- **Client accounts:** central admin creation and client/branch scope remain. Generic "user access control" did not authorise inventing client self-service user administration.
- **Provider integrations:** digital verification, OCR/identity comparison, MCA/GST/PAN/court/watchlist/media checks, HRMS, campaign delivery and automatic source ingestion need their own implementation, permissible access and configured providers. Recorded provider evidence is not a live API integration.
- **Later phases:** AI assistance and optional commissions were not added. No model is used to make independent hiring, character or rejection decisions; no continuous tracking is introduced.
- **Delivery and storage:** outbox/notifications, object-storage adapters and configurable malware scanning exist. Enabled workers, real delivery, scanner responses, access policies, backups/restoration and object deletion must be tested in the target deployment. An optional dependency or acknowledged queue item is not delivery evidence.
- **Browser and scale:** backend/UI implementation and focused tests do not certify all multi-role browser flows, device layouts, actual provider responses or unlimited document/photo volume. Run the agreed browser UAT and realistic upload/concurrency/export tests. No blanket claim that every slow API has been fixed is made.
- **Database/deployment:** source code and migrations being present do not establish what is currently deployed. Use the main handoff for actual migration/build/typecheck/unit/rollback-test results and deployment instructions; this status document did not run broad checks, start servers or mutate live data.

The core workflow, proposals, source outreach, contract evidence, collections and privacy governance are materially extended. Public-inquiry/deck automation, richer specialisation, native background Excel imports, full provider coverage, broader privacy execution and deployment/scale checks still remain. Do not present this register as "all complete" or a production/security/compliance certification.
